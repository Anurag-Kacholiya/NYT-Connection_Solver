How It All Works — Feature Extraction, Scoring & Model Choices

A plain-English walkthrough of what the system actually does, step by step — no ML background needed.

🧩 The core problem

You have 16 words. They secretly belong to 4 groups of 4. You need to figure out which 4 words belong together. The catch: there are 1,820 possible ways to pick a group of 4 from 16 words (that's C(16,4)). The system has to score all of them and find the right 4.

Step 1 — Building Similarity Matrices

🔗 What is a similarity matrix?

Before we can score groups, we need to know how similar every word is to every other word. For each of the 17 different signals (semantic, phonetic, knowledge-graph, etc.), we build a 16×16 grid where each cell tells us "how similar are word i and word j according to this signal?"

Example: MPNet similarity matrix for 4 words (simplified)
PIANO GUITAR HAMMER DRILL
PIANO 1.00 0.82 0.12 0.09
GUITAR 0.82 1.00 0.11 0.08
HAMMER 0.12 0.11 1.00 0.79
DRILL 0.09 0.08 0.79 1.00
■ High similarity (same group)    ■ Low similarity (different groups)

High values inside the correct groups, low values between groups — that's the ideal pattern. The system builds 17 such matrices per puzzle (one for each signal type) and then double-centers each one to remove global bias.

Why 17 different matrices? No single signal works for all NYT puzzle types. GloVe catches word meanings, phonetics catches rhymes and homophones, Wikidata catches factual categories (e.g. "all Olympic sports"), Wikipedia catches membership (e.g. "all Beatles songs"). The puzzle designers deliberately exploit many types of connections.
Step 2 — Extracting Features from Each Candidate Group

🔬 Turning matrices into numbers the models can use

For each of the 1,820 candidate groups of 4, we extract 9 features from each of the 17 matrices = up to 153 numbers that describe that group. Think of it like filling out a 153-column questionnaire for every possible group.

Here is what each of the 9 features means in plain English, using the group {PIANO, GUITAR, VIOLIN, DRUMS} as an example:

mean_in Average similarity inside the group

Average of all 6 pairwise similarity scores between the 4 words. For {PIANO, GUITAR, VIOLIN, DRUMS} this is high because they're all instruments. Higher = group is cohesive.

min_in The weakest link inside the group

The lowest similarity score among the 6 pairs. If even the least-similar pair inside the group is still quite similar, that's a very tight group. A bad group will have at least one pair that doesn't fit. Higher = no weak links.

var_in How consistent the similarities are inside

Variance of the 6 pairwise scores. A tight, uniform group (all pairs equally similar) has low variance. A group with one odd-word-out has high variance. Lower = more uniform group.

max_out How close the group is to the nearest outsider

Maximum similarity between any group member and any word outside the group. If BASS is in the group and also very similar to BASS GUITAR (an outsider), max_out will be high — a warning sign that the group might be confused. Lower = less confusion risk.

separation The main signal — how much better inside than outside

mean_in − mean_out. This is the most important single feature. It asks: "Are the 4 words more similar to each other than to the 12 outsiders?" A high positive separation means the group is clearly distinct. A group with separation near zero is ambiguous.

second_max_out The 2nd most dangerous outsider

One strong outsider similarity might be a fluke. If the 2nd highest is also large, there are multiple confusing words outside — the group is genuinely ambiguous, not just unlucky. Lower = safer group.

avg_top3_out Average of the top 3 outsider threats

Mean of the 3 most similar outsider pairs. A broader measure of how many words outside the group are trying to "steal" members from it. Lower = cleaner boundary.

group_ambiguity How "pulled" group members are towards outsiders

For each of the 4 group members, compute their average similarity to all 12 outsiders. Sum these up. If a group member is generally similar to lots of other words in the puzzle, it's a generic word that could fit anywhere — making the group harder to pin down. Lower = more specific, less ambiguous group.

triangle_score Structural coherence — do similarities "make sense together"?

Logic test: if A is similar to B, and B is similar to C, then A should be similar to C too. For every triplet (a,b,c) in the group, checks if this triangle is consistent. A real group should be coherent — all members related to each other, not just in a chain. Higher = more internally coherent.

Total features per candidate group: 9 features × 17 matrices = 153 features. For one puzzle, that's 1,820 groups × 153 features = 278,460 numbers computed, just to score one puzzle.
Step 3 — The 4-Layer Decision Hierarchy

🏛️ How the 4 models fit together

Each model plays a different role in the decision process. They don't all do the same job — they form a hierarchy where each layer refines the previous one.

LAYER 1 RF & GBM — Discovery

Look at each candidate group independently. Ask: "Is this a correct group? Yes or No?" They are pointwise experts — they score each of the 1,820 groups in isolation without knowing what the others scored.

LAYER 2 LightGBM Ranker — Ranking

Doesn't look at candidates in isolation — it sees all 1,820 candidates for a puzzle together and asks: "Which of these is the BEST one relative to the others?" If RF and GBM both say "90% likely" for two groups, the ranker is the one that says "this one is 92%, that one is 89%." It is the re-ranker that breaks ties and applies context.

LAYER 3 LR Fusion — Coordination

Sits alongside the others and asks: "Which of the 17 similarity signals should I trust today?" It learned (on the validation set) that e.g. MPNet separation is a strong signal and morphological similarity is weak. It weights the raw matrix evidence before feeding into the final score — acting as the ensemble manager that keeps noisy signals from corrupting the decision.

LAYER 4 solve_ml() — Strategy

Takes all the weighted scores from Layers 1–3 and asks: "How do I fit 4 groups together so they all work as a complete partition of 16 words?" It prevents choosing a high-scoring group that "steals" a word that belongs to another group. Without this layer, a greedy approach could win one group and ruin three others.

🔍 Layer 1 — RF & GBM: The Detectives (Pointwise Scorers)

Both models do the same job — score each group independently — but they approach it differently, which is why both are kept.

Random Forest

Trains 200 decision trees in parallel, each on a random data + feature subset. All trees vote — the vote fraction becomes the probability. Very stable, hard to overfit, good when many features are irrelevant.

Output: probability 0–1  ·  Weight: 15%
Gradient Boosting

Builds 200 trees sequentially — each new tree specifically targets the mistakes of the previous ones. More sensitive to subtle patterns and difficult edge cases. Complements RF because they make different errors.

Output: probability 0–1  ·  Weight: 15%
What "pointwise" means in code: clf_rf.predict_proba(feats_arr)[:, 1] and clf_gbm.predict_proba(feats_arr)[:, 1] — each row of feats_arr is one candidate group, scored completely independently. The model never sees the other 1,819 candidates when scoring any one of them.

🏆 Layer 2 — LightGBM Lambdarank: The Judge (Re-ranker)

The key insight behind choosing a ranker: we don't need to know the absolute probability that a group is correct — we need to know which group is more likely correct than the others in this specific puzzle. That's a ranking problem, not a classification problem.

Treats each puzzle as a "query", all 1,820 candidates as "documents to rank"
Optimises NDCG — ranks correct groups at the top within each puzzle
Breaks ties RF and GBM can't — if two groups both score 90%, the ranker picks the better one
Gets 50% weight because of this — it is the dominant signal
Training labels (3-level relevance)
label 2 Correct group — this is what we want ranked #1
label 1 Hard negative — 3/4 overlap, almost right but wrong
label 0 Easy negative — random wrong group
Output: ranking score (not a probability)
Weight in ensemble: 50%
Code detail: probs_ranker = clf_ranker.predict(feats_arr) — then min-max normalized to [0,1] so it can be combined with RF/GBM probabilities in the weighted average. All 1,820 candidates are scored (not just 120 — the top_k=120 parameter in generate_candidates is accepted but currently unused).

⚖️ Layer 3 — LR Fusion: The Taskmaster (Signal Coordinator)

LR Fusion has a completely different input from the other three models. It doesn't receive the full 153-feature vector — it only receives 17 numbers (the separation score from each matrix). It learns: "When these 17 signals conflict, which ones should I trust?"

Only 17 parameters — one learned weight per similarity matrix
Trained on validation set only — never saw training data
Fully interpretable — you can read the coefficients directly from the saved model
Keeps noisy/redundant signals from corrupting the final score
What it learns (example learned weights)
MPNet_separation +5.28 ✦ trust this
WikiData_separation +3.91 ✦ trust this
GloVe_separation +1.44
Morphological_separation +0.02 ≈ ignore
Output: probability 0–1
Weight in ensemble: 20%

🧩 Layer 4 — solve_ml(): The Strategist (Global Partition Optimizer)

Even after perfect scoring, a greedy approach fails in one specific scenario: when the highest-scoring group "steals" a word that's actually needed by another group. solve_ml() prevents this.

The problem it solves: Group A scores 0.95 and is picked greedily. But word "BASS" in Group A actually belongs to Group B (score 0.90). Now Group B has only 3 correct words — it can never score well. Groups C and D also suffer. Total score collapses.

The solution: Find the 4-partition of all 16 words that maximises the sum of all 4 group scores — not just the best single group. Sometimes choosing Group A' (score 0.88) instead of A lets B', C', D' all score highly, giving a better total.

When is it triggered?
top score < 0.70

Model is uncertain → run solve_ml() on top-250 candidates → submit the entire optimal 4-partition at once

top score ≥ 0.70

Model is confident → skip solve_ml, greedy pick is safe and faster

This is in solver.py, called from evaluate.py's simulate_game_ml()
Step 3b — What Each Model is Actually Trying to Learn (Objective Functions)

🎯 Why objective functions matter

Every ML model needs a loss function — a number that measures "how wrong am I right now?" Training is the process of minimising that number. Different loss functions teach models to be good at different things. Here's what each model is optimising, with a concrete Connections example.

Our running example puzzle: 16 words including PIANO, GUITAR, VIOLIN, DRUMS, BASS, HAMMER, DRILL, SAW, CHISEL, APPLE, MANGO, GRAPE, PEACH, CLOUD, RAIN, THUNDER. Correct groups: {instruments}, {tools}, {fruits}, {weather}.

🌲 RF Objective — Gini Impurity

At every split in every decision tree, the RF asks: "Which feature threshold most cleanly separates correct groups from wrong groups?" It measures "cleanliness" using Gini impurity.

Formula
Gini = 1 − p(correct)² − p(wrong)²
Lower Gini = purer split = better. Gini = 0 means perfectly separated. Gini = 0.5 means total chaos (50/50 mix).
Concrete example from our puzzle:
The tree considers the split: MPNet_sim_separation > 0.35
ABOVE threshold (separation > 0.35)
320 candidate groups land here
240 are correct groups
80 are wrong groups
Gini = 1 − (240/320)² − (80/320)²
= 1 − 0.5625 − 0.0625 = 0.375
BELOW threshold (separation ≤ 0.35)
1500 candidate groups land here
40 are correct groups
1460 are wrong groups
Gini = 1 − (40/1500)² − (1460/1500)²
= 1 − 0.0007 − 0.9484 = 0.0509
Weighted average Gini = 0.375 × (320/1820) + 0.0509 × (1500/1820) = 0.108 — a very clean split! The tree keeps this split.
What this means for our puzzle: The RF learns that {PIANO, GUITAR, VIOLIN, DRUMS} has MPNet_separation = 0.71 → lands well above the threshold → tree votes "correct". The group {PIANO, GUITAR, VIOLIN, BASS} has MPNet_separation = 0.48 → also above, but other trees with other features will vote it down.

📈 GBM Objective — Log Loss (Binary Cross-Entropy)

GBM trains sequentially. Each round adds a new tree that specifically fixes the errors of the previous ensemble. The loss it minimises is log loss — which punishes confident wrong answers much more severely than uncertain wrong answers.

Formula
Loss = −[y·log(p) + (1−y)·log(1−p)]
y = true label (1=correct, 0=wrong), p = predicted probability. Lower loss = better.
Concrete example from our puzzle:
Round 1 — initial predictions:
Candidate group True label Predicted p Log Loss Status
{PIANO, GUITAR, VIOLIN, DRUMS} 1 (correct) 0.85 0.163 ✓ good
{PIANO, GUITAR, VIOLIN, BASS} 0 (wrong) 0.80 1.609 ✗ very wrong — confidently wrong!
{HAMMER, APPLE, RAIN, PIANO} 0 (wrong) 0.05 0.051 ✓ correctly uncertain
Round 2 focuses on: {PIANO, GUITAR, VIOLIN, BASS} because it had the highest loss (1.609). The next tree is trained specifically to push that group's score DOWN by learning what feature distinguishes it from the real instruments group — e.g. WordNet_sim_min_in is lower because BASS has musical AND fish senses.
Key insight: GBM is specifically designed to handle the "close but wrong" decoy groups (3/4 overlap) — exactly the hard negatives in our training set. Each round zooms in on whichever decoy group is currently fooling the model most.

🏆 LightGBM Objective — NDCG@[1,3,5] (Ranking Quality)

NDCG = Normalised Discounted Cumulative Gain. It measures: "Are the correct groups sitting at the top of our ranking?" Getting rank #1 right is worth more than getting rank #5 right.

Intuition
DCG = Σ relevance(rank_i) / log₂(rank_i + 1)
NDCG = DCG / ideal_DCG   (normalised so max = 1.0)
Relevance: correct group=2, hard-wrong=1, easy-wrong=0. Rank 1 counts most, rank 5 counts less.
Concrete example from our puzzle:
For our puzzle, after scoring all 1,820 candidates, the top-5 ranked groups look like this in two scenarios:
BAD RANKING (low NDCG)
#1 {PIANO,GUITAR,VIOLIN,BASS} rel=1
#2 {PIANO,GUITAR,BASS,DRUMS} rel=1
#3 {PIANO,GUITAR,VIOLIN,DRUMS} rel=2
#4 {HAMMER,DRILL,SAW,PIANO} rel=0
#5 {HAMMER,DRILL,SAW,CHISEL} rel=2
NDCG@3 ≈ 0.61 — correct group buried at #3
GOOD RANKING (high NDCG)
#1 {PIANO,GUITAR,VIOLIN,DRUMS} rel=2
#2 {HAMMER,DRILL,SAW,CHISEL} rel=2
#3 {APPLE,MANGO,GRAPE,PEACH} rel=2
#4 {PIANO,GUITAR,VIOLIN,BASS} rel=1
#5 {CLOUD,RAIN,THUNDER,BASS} rel=0
NDCG@3 ≈ 0.97 — correct groups at #1, #2, #3
The lambdarank trick: If {PIANO, GUITAR, VIOLIN, BASS} (wrong) is ranked above {PIANO, GUITAR, VIOLIN, DRUMS} (correct), swapping them gains a lot of NDCG. The model learns a large gradient update specifically for this swap — pushing the correct group higher and the decoy lower. RF and GBM can't do this because they never compare the two candidates against each other.

⚖️ LR Fusion Objective — Log Loss + L2 Regularisation

LR Fusion uses the same log loss as GBM, but on a much simpler input — just 17 numbers (one separation score per matrix). The L2 penalty keeps the 17 weights small so no single matrix dominates unfairly.

Formula
Loss = −[y·log(p) + (1−y)·log(1−p)] + (1/C)·Σw²
C=1.0, class_weight="balanced" (upweights rare correct groups)
Concrete example from our puzzle:
For candidate group {PIANO, GUITAR, VIOLIN, DRUMS}, the 17 separation scores are computed:
MatrixSeparationLR weightContribution
MPNet_sim0.71+5.28+3.75 ← big push toward "correct"
WikiData_sim0.62+3.91+2.42 ← "musical instruments" wikidata category matches
GloVe_sim0.44+1.44+0.63
Morphological_sim0.03+0.02+0.001 ← nearly ignored
Phonetic_sim0.08+0.05+0.004 ← ignored (rhyming irrelevant here)
p = sigmoid(3.75 + 2.42 + 0.63 + 0.001 + ...) = sigmoid(7.1) = 0.9992 → very likely correct ✓
Now for the decoy group {PIANO, GUITAR, VIOLIN, BASS}:
MPNet_sim0.65+5.28+3.43 ← still high, BASS sounds musical
WikiData_sim0.18+3.91+0.70 ← BASS wikidata = fish + music, category unclear
GloVe_sim0.38+1.44+0.55
p = sigmoid(3.43 + 0.70 + 0.55 + ...) = sigmoid(5.0) = 0.993
What LR fusion caught that others missed: The WikiData separation dropped from 0.62 → 0.18 for the BASS decoy group because BASS has conflicting Wikidata properties (fish vs. instrument). LR learned that WikiData_separation is a high-weight signal (+3.91), so this drop dramatically reduces the decoy's score — even though MPNet didn't catch it (BASS still sounds like a musical word).

📊 Objective function summary

Model Objective Sees candidates as Best at catching
RF Gini impurity (minimise) Independent, isolated Clear-cut obvious groups with high separation
GBM Log loss (minimise) Independent, isolated Subtle decoys — learns from its own confident mistakes round by round
LightGBM NDCG@[1,3,5] (maximise) Compared against all 1,820 in the same puzzle Tie-breaking between near-identical candidates — puts the right one on top
LR Fusion Log loss + L2 (minimise) Independent, but only 17 matrix signals Polysemous words (BASS, CLOUD) where some signals mislead and others reveal truth
Why all 4 together? RF provides stable baseline probabilities. GBM sharpens on hard decoys. LightGBM re-ranks within the puzzle context. LR Fusion down-weights noisy signals. Each failure mode of one model is covered by another — which is the entire point of an ensemble.
Step 3c — What Each Model is Actually Trying to Minimise During Training

🎯 What is an objective function?

Every time a model trains, it needs to measure "how wrong am I right now?" so it can fix itself. The objective function is that measurement. Training = repeatedly computing this number and adjusting the model's internal parameters to make it smaller (or larger). The choice of objective function decides what the model gets good at.

Our setup: For each puzzle we have 1,820 candidate groups. Of those, exactly 4 are correct (label = 1) and 1,816 are wrong (label = 0). Each model sees this extreme imbalance and needs its own strategy to handle it.

🌲 Random Forest — Minimises Gini Impurity at every tree split

The RF doesn't have one single global loss function. Instead, each individual tree split asks: "Which feature + threshold creates the cleanest separation between correct and wrong groups on this side vs. that side?" Gini impurity measures that cleanliness.

Formula
Gini = 1 − p(correct)² − p(wrong)²
Gini = 0.5
worst possible
50/50 mix — no information
Gini = 0.3
decent split
some separation
Gini = 0.0
perfect split
all correct on one side
What this means in our puzzle:

The tree asks: "Should I split on MPNet+Numberbatch_min_in > 0.35?"

Left side — min_in > 0.35

{PIANO, GUITAR, VIOLIN, DRUMS} lands here — all 6 pairs are strongly similar. min_in = 0.71 ✓

Say: 300 groups here
280 correct, 20 wrong
Gini = 1 − (280/300)² − (20/300)²
= 0.121 ← very clean
Right side — min_in ≤ 0.35

{PIANO, GUITAR, VIOLIN, BASS} lands here — BASS–VIOLIN pair is weak. min_in = 0.28 ✗

Say: 1520 groups here
4 correct, 1516 wrong
Gini = 1 − (4/1520)² − (1516/1520)²
= 0.005 ← also clean (mostly wrong)
Weighted Gini = 0.121×(300/1820) + 0.005×(1520/1820) = 0.024 — excellent split! The tree keeps this. This is exactly why MPNet+Numberbatch_min_in is ranked #1 in feature_weights.txt with 25.28% average importance.
What the RF is trying to do: Find as many clean splits as possible across 200 trees, each using a random subset of features. The result is a probability — what fraction of all 200 trees said "yes, this is a correct group" for a given candidate.

📈 Gradient Boosting — Minimises Log Loss (Binary Cross-Entropy)

Log loss is the most common loss for binary classification. It measures not just whether you got it wrong, but how confidently wrong you were. Being 99% confident on a wrong answer is penalised far more than being 51% confident on a wrong answer.

Formula
Loss = −[ y · log(p) + (1−y) · log(1−p) ]
where y = true label (1 = correct group, 0 = wrong group), p = what the model predicted
How this plays out in 4 concrete cases:
True label Model predicted Loss Meaning
y=1 (correct) p=0.90 0.105 Correctly confident ✓ tiny penalty
y=1 (correct) p=0.20 1.609 Missed a correct group ✗ big penalty
y=0 (wrong) p=0.05 0.051 Correctly rejected ✓ tiny penalty
y=0 (wrong) p=0.85 1.897 Confidently wrong ✗ biggest penalty
What this means in our puzzle:

Round 1: Model predicts {PIANO, GUITAR, VIOLIN, BASS} = 0.85 (confidently wrong). Loss = 1.897. This is the biggest error right now.

Round 2: GBM trains a new tree specifically to fix this — it studies what's different between {PIANO, GUITAR, VIOLIN, BASS} and {PIANO, GUITAR, VIOLIN, DRUMS}. It finds that MultiSense_sim_min_in is lower for the BASS group because BASS has a fish sense that pulls its multi-sense embedding away from instruments. The new tree pushes the BASS group's score down.

After 200 rounds: GBM has iteratively fixed every confidently-wrong prediction. It becomes very good at the subtle "almost right" decoys — which is why MultiSense and WordNet features dominate its importance.
Key difference from RF: RF builds 200 independent trees all at once. GBM builds 200 trees in sequence, each one correcting the previous. GBM is slower to train but much sharper on hard cases.

🏆 LightGBM Lambdarank — Maximises NDCG@[1,3,5]

This is the most different objective. RF and GBM both ask "is this group correct?" — they treat each candidate in isolation. LightGBM asks "given all 1,820 candidates for this puzzle, can I rank the 4 correct ones at the very top?" This is a fundamentally different problem.

NDCG — Normalised Discounted Cumulative Gain
DCG = Σ relevance(i) / log₂(rank(i) + 1)
NDCG = DCG / ideal_DCG   (1.0 = perfect ranking)
Relevance: correct group = 2, hard-wrong (3/4 overlap) = 1, easy-wrong = 0. Rank 1 counts most, rank 100 counts little. The model is penalised more for burying a correct group at rank 10 than at rank 5.
What this means in our puzzle — a step-by-step example:

Imagine after initial training, our top-5 ranked candidates for one puzzle look like this:

#1 {PIANO, GUITAR, VIOLIN, BASS} rel = 1 WRONG (decoy)
#2 {PIANO, GUITAR, VIOLIN, DRUMS} rel = 2 CORRECT ✓
#3 {HAMMER, DRILL, SAW, CHISEL} rel = 2 CORRECT ✓
#4 {APPLE, MANGO, GRAPE, PEACH} rel = 2 CORRECT ✓
#5 {CLOUD, RAIN, THUNDER, DRIZZLE} rel = 2 CORRECT ✓
The lambdarank calculation: Swapping rank #1 (wrong, rel=1) with rank #2 (correct, rel=2) would gain ΔNDCG = +0.22. Swapping rank #3 with rank #5 only gains ΔNDCG = +0.04. The model assigns a much larger gradient to the #1/#2 swap — it focuses its update on fixing the most damaging mistake first. This is the "lambda" in lambdarank.
After training: The model learns that {PIANO, GUITAR, VIOLIN, BASS} should always rank below {PIANO, GUITAR, VIOLIN, DRUMS} — and it learns this by seeing this scenario across hundreds of training puzzles where BASS keeps appearing as a decoy.
@[1,3,5] means: The model evaluates NDCG at rank 1, rank 3, and rank 5. Getting rank #1 right matters most. If a correct group is at rank 6, it's basically invisible to this objective.
Why RF/GBM can't do this: They score each of the 1,820 candidates independently. They never compare {PIANO, GUITAR, VIOLIN, BASS} against {PIANO, GUITAR, VIOLIN, DRUMS} within the same training step. LightGBM does — and that's its entire advantage.

⚖️ Logistic Regression Fusion — Minimises Log Loss + L2 Regularisation

LR Fusion also uses log loss — same formula as GBM — but on a much simpler input. It only receives 17 numbers per candidate (one separation score per matrix). The L2 penalty is the key addition that prevents any one matrix from taking over.

Formula
Loss = −[ y·log(p) + (1−y)·log(1−p) ]  ← same as GBM
+ (1/C) · Σ w²                            ← L2 penalty (new)
C=1.0 controls L2 strength. class_weight="balanced" automatically upweights the 4 correct groups to compensate for the 1,816 wrong ones — without this, the model would just learn to always predict "wrong" and get 99.8% accuracy.
What the L2 penalty actually does:

Imagine without L2, the model found that MPNet separation alone perfectly separates correct from wrong on the validation set. It might assign w = +50 to MPNet and w ≈ 0 to everything else. That's overfitting to one signal. The L2 penalty adds (1/1.0) × 50² = 2500 to the loss — making this extreme weight very costly. The model is forced to spread the weight more evenly across signals that actually help.

Matrix signalWithout L2With L2 (C=1.0)
MPNet_separation w = +50.0 w = +5.28
WikiData_separation w ≈ 0.0 w = +3.91
Morphological_separation w ≈ 0.0 w = +0.02
The L2 version is more honest — it gives credit to WikiData when it helps, rather than ignoring it just because MPNet is already strong on its own.
What LR is actually minimising: The total log loss across all candidate groups in the validation set, plus a penalty for any weight that gets too large. The 17 learned weights are the answer to: "Which signals, when combined linearly, best predict whether a group is correct — while staying simple enough to not overfit?"

📊 Side-by-side comparison of all 4 objectives

Model Objective Direction What it punishes hardest What it ignores
RF Gini impurity per split Minimise Unclear splits — features that don't separate classes well How confident the final vote is — just counts tree votes
GBM Log loss (total) Minimise Confident wrong predictions — gets huge penalty for high p on a wrong group Relative ranking between candidates — each scored independently
LightGBM NDCG@[1,3,5] Maximise Correct groups ranked low — especially if a wrong group outranks them Absolute probability values — only cares about order within the puzzle
LR Fusion Log loss + L2 Minimise Confidently wrong + large weights (L2 shrinks all weights toward zero) Complex feature interactions — it's a linear model, only sees 17 numbers
The deeper reason we use all 4: Gini tells us which features are most discriminative. Log loss tells us to not be overconfident on wrong groups. NDCG tells us to rank correct groups above wrong ones in each puzzle context. L2 regularisation tells us not to trust any one signal too much. No single objective captures all of these requirements — so we use all four and combine them.
Step 4 — Combining Scores and Picking the Best Group

🎛️ How the final score is computed for each group

Each of the 1,820 candidate groups gets a final score assembled from all 4 models:

Full ensemble (all 4 models available)
base_score = 0.15 × RF + 0.15 × GBM + 0.50 × LightGBM_ranker + 0.20 × LR_fusion
Then a small bonus is added:
final_score = base_score + 0.05 × (1/rank) + 0.05 × gap_to_next_best
These bonuses are tiny (0.05 weight) — they slightly favour candidates already ranked highly and well-separated from competitors, without overriding the ML score.

After scoring all 1,820 groups, one of two things happens:

If top score ≥ 0.70 — Confident → Greedy

The model is confident about its top pick. Just take that group, remove those 4 words, and repeat for the remaining 12, 8, and 4 words. Fast and simple.

If top score < 0.70 — Uncertain → Global Optimiser

The model is unsure. Instead of greedily picking one group, it asks: "What combination of 4 groups gives the best total score?" solve_ml() finds this optimal 4-way partition — preventing one good-looking group from blocking the others.

The uncertainty check: There's also a per-candidate uncertainty filter. If the 4 models strongly disagree on a candidate (std > 0.25 across their scores), that candidate is skipped in greedy mode — even if it has a high average score, disagreement signals it's risky to commit to.
Putting It All Together — End-to-End for One Puzzle

🗺️ Complete walkthrough for a single puzzle

1. Load 16 words from the puzzle (data_loader.py)
2. Build 17 similarity matrices — one API/embedding call per signal type (embedder.py). Each matrix is 16×16.
3. Double-center all 17 matrices to remove global bias (evaluate.py)
4. Enumerate all 1,820 possible groups of 4 from the 16 words (evaluate.py)
5. For each group: extract 153 features (9 features × 17 matrices). Result: a 1820×153 matrix (evaluate.py)
6. Run all 4 models on those 1820×153 features. Get 4 score arrays of size 1820. (evaluate.py)
7. Combine into one base_score per group using the weighted ensemble formula
8. Apply rank bonus + gap bonus → final adjusted_score per group
9a. If top score ≥ 0.70: take the highest-scoring group greedily, remove 4 words, repeat
— or —
9b. If top score < 0.70: pass top-250 candidates to solve_ml() → find the 4-partition that maximises total score → submit all 4 groups at once (solver.py)

Feature Importance Analysis — What the Models Actually Learned

Ranked Gini impurity decrease (averaged across RF + GBM) for all 153 features. From feature_weights.txt. Read this to see which similarity matrices matter most — and which ones are broken or useless.

🧠 How to read this

After training, we compute Gini importance for each of the 153 features in the RF and GBM models. Gini importance measures: "How much did splitting on this feature reduce the impurity across all decision tree nodes?" A feature used at many high-level splits has high importance. A feature never used (or used only at leaf level) has near-zero importance.

The importances are normalised so they sum to 1.0 per model. We average RF and GBM importances to get a combined rank. 153 features = 9 features × 17 similarity matrices. The table below tells us which matrices and which feature types actually drive correct predictions.

💡 Why is min_in the #1 feature by a huge margin?

Think about how Connections puzzles work. A group is valid if and only if all 4 words belong together. The model is penalised most when one word is an outlier in the group. min_in directly measures "how similar is the worst pair?" — it captures exactly this.

Wrong group example

Candidate: {PIANO, GUITAR, VIOLIN, BASS}

min_in = sim(BASS, VIOLIN) ≈ 0.12 — BASS (fish) doesn't fit

The minimum similarity is very low → model predicts ❌ not a group

Correct group example

Candidate: {PIANO, GUITAR, VIOLIN, CELLO}

min_in = sim(PIANO, GUITAR) ≈ 0.71 — all are string/keyboard instruments

Even the weakest pair has high similarity → model predicts ✅ correct group

📉 triangle_score — the nearly useless feature

Every matrix has a triangle_score feature. In theory it measures transitivity: if A→B and B→C are both similar, is A→C also similar? (A triangle of mutual similarity is a sign of a coherent group.)

In practice, it adds almost nothing. Top triangle_score values from the table:

Why is triangle_score so useless? After double-centering the matrix, the scores already capture within-group vs. out-of-group structure. Triangle transitivity doesn't add new information — the min_in, mean_in, and separation features already encode the same signal more directly. The triangle_score features are candidates for removal in future versions to reduce noise.

🔑 Key Takeaways from Feature Importance

1. MPNet+Numberbatch + MultiSense carry ~66% of the total predictive power. If you had to keep only 2 matrices, these are the two. Numberbatch's lexical knowledge boosts raw MPNet significantly — worth the extra computation.
2. min_in is the king of features. Across all matrices, the minimum internal similarity dominates. A group is only as strong as its weakest pair. This makes intuitive sense for Connections: one outlier word breaks the whole group.
3. ConceptNet is dead weight. 9 features, all 0.0000. The SQLite DB is missing or empty. This is wasted feature space — removing ConceptNet from the pipeline would make feature extraction faster with zero accuracy loss.
4. triangle_score features add almost no value. Best case is 0.03% contribution. These 17 features (one per matrix) are candidates for removal to reduce noise and computation.
5. GBM is more aggressive than RF. GBM puts 33.25% of all importance on a single feature (MPNet+Numberbatch_min_in). RF spreads importance more evenly. This is why averaging them helps — GBM's concentration and RF's diversity are complementary.

embedder.py

Converts 16 words into similarity matrices using 17 distinct signals. Of the 21 methods defined, only 17 are actually wired into the pipeline.

🎯 Role

For every puzzle, the embedder produces a set of 16×16 pairwise similarity matrices. Each matrix[i][j] encodes how similar word i and word j are according to one signal (semantic, lexical, phonetic, knowledge-graph etc.). These matrices go directly into evaluate.py's build_matrices().

Caching: All expensive external API calls (Wikidata, Wikipedia, Datamuse) are fired once per 16-word grid via _ensure_grid_cache(). Wikidata is fetched sequentially (polite); Wikipedia and Datamuse are fetched in parallel ThreadPoolExecutors.

evaluate.py

Pure library. Defines feature extraction, the 3-stage ML simulation pipeline, and the training loop. Imported by train.py — never run directly.

🎯 Role

This file bridges embedder and solver. It answers: "Given similarity matrices, what numerical features describe each group-of-4? How do we score those features with ML models? How do we play a game turn by turn?"

📐 double_center(mat) — preprocessing applied to every matrix

double_center(mat) = mat − row_mean − col_mean + global_mean

Removes global bias so words that are "similar to everything" don't dominate. Applied to all 17 matrices before any features are computed. Analogous to kernel centering in Kernel PCA.

🎮 simulate_game_ml() — 3-Stage Pipeline (the core game loop)

Stage 1 — Candidate generation: All C(16,4) = 1,820 possible groups-of-4 are enumerated via generate_candidates(). No pruning — every candidate is scored.
Stage 2 — ML ensemble scoring (4 combinations depending on which models are available): 
# All 4 models (full ensemble)
score = 0.15·RF + 0.15·GBM + 0.50·LightGBM_ranker + 0.20·LR_fusion

# Ranker but no LR fusion
score = 0.20·RF + 0.20·GBM + 0.60·LightGBM_ranker

# LR fusion but no ranker
score = 0.35·RF + 0.35·GBM + 0.30·LR_fusion

# RF + GBM only
score = (RF + GBM) / 2
Stage 2b — Competition-aware adjustments: 
adjusted[g] = base_score[g] + 0.05·(1/rank(g)) + 0.05·gap_to_next(g)
Small bonuses so high-confidence, well-separated candidates are preferred. α = β = 0.05 keeps ML score dominant.
Stage 3 — Global optimisation (only if top score < 0.70): Calls solve_ml() from solver.py on top-250 candidates to find the 4-partition that maximises total adjusted score. Submits groups in decreasing score order. If the top candidate scores ≥ 0.70, skips to greedy (high confidence → commit directly).
Uncertainty filter: std([RF, GBM, ranker, LR]) > 0.25 → models disagree → skip this candidate in greedy fallback. Forces a safer pick if models conflict.

solver.py

Pure library. Called by evaluate.py's simulate_game_ml(). Finds the globally optimal 4-partition using memoized recursive search.

🎯 Role

A greedy approach (pick the highest-scoring group, remove it, repeat) risks committing to a group that blocks better overall partitions. solve_ml() searches for the 4-partition of all 16 words that maximises the sum of adjusted scores across all 4 groups simultaneously.

When is it called? Only during the very first turn of a game (all 16 words remain) AND only when the top individual candidate scores < 0.70. If the model is confident, greedy is used instead.

🔧 solve_ml() — memoized DP partition search

ParameterTypeDescription
score_lookupDict[Tuple, float]Adjusted scores for candidate groups. Keys = sorted tuples of word indices. Missing groups default to −1e9.
itemsSet[int]Word indices still remaining. Usually {0..15} on the first call.
→ returnstuple(best_partition: list[tuple], best_score: float)
algorithm
Base: 0 items → ([], 0.0). 4 items → single lookup.
Fix the lowest-index item. Try all C(n−1, 3) groups containing it.
For each candidate: group_score + recurse(remaining items).
Memoize by frozen sorted remaining-item tuple. Each sub-problem solved once.

Fixing the lowest-index item at each level eliminates symmetric orderings, making the search tractable. Only the top-250 candidates (by score) are passed in from evaluate.py to limit the search space.

eval_only.py

Standalone script. Re-runs the full evaluation (val + test) using saved .pkl models — without retraining. Use this when you want to test different model folders or re-run eval after code changes.

🎯 Role

The training step is expensive (hours of feature extraction + model fitting). eval_only.py lets you skip it entirely and jump straight to evaluation using models already saved on disk.

When to use this instead of train.py: You've already trained, you changed a flag in simulate_game_ml, you want to compare two different saved model directories, or you want to run evaluation on a different CSV without retraining.

🔧 Parameters (CLI arguments)

ArgumentDefaultDescription
--csvConnections_Data.csvPath to the data file

usage
# Default — uses models/ directory
python eval_only.py

# Point at a different trained model set
python eval_only.py --models-dir aug_models_suparshwa

# Different CSV + model dir
python eval_only.py --csv Connections_Data.csv --models-dir models

eval_only.py uses the full pipeline (including LR fusion and solve_ml) — it delegates entirely to evaluate_split() from train.py, which calls simulate_game_ml() from evaluate.py with all 4 models. This is different from evaluate_test_advanced.py which uses a simpler 1/3 average ensemble and no global optimizer.

Key corrections from first version of this report
① evaluate.py and solver.py are libraries called by train.py, not scripts run after it.
② embedder.py has 3 dead/stub methods: get_knowledge_graph_ppr_similarity() returns zeros; get_phrase_completions() and get_explicit_categories() are empty pass stubs.
③ evaluate_test_advanced.py uses a simple (RF+GBM+LGBM)/3 average — no LR fusion, no solve_ml, no score adjustments.
④ get_wikipedia_categories_similarity() is defined twice in embedder.py; the second definition (line ~711) silently overrides the first.
⑤ eval_only.py was missing from the original report — it is a legitimate 7th entry point for evaluation without retraining.
